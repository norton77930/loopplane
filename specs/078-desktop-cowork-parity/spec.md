# Feature Specification: Desktop Cowork Parity

**Feature Branch**: `main`

**Created**: 2026-07-30

**Status**: Draft

**Input**: Upgrade the existing local desktop shell into a first-class cowork application with safe local process ownership, versioned communication, reusable conversation and settings experiences, workspace-aware sessions, multi-pane inspection, turn audit, and recoverable local backup/restore while preserving existing runtime boundaries.

## Clarifications

### Session 2026-07-30

- Q: How should portable backups reconcile full session history with user-authored paths or secrets? → A: Preserve authorized user-, model-, and tool-produced history plus eligible referenced artifacts losslessly, exclude LoopPlane-owned credentials/configuration/private path mappings and direct/recursive workspace collection, exclude unsent drafts, and explicitly warn that sensitive values or workspace excerpts may remain in the unencrypted backup.
- Q: How should clean-install packaging obtain PyInstaller without adding a runtime dependency? → A: Use a two-stage gate: narrowly authorize deterministic materialization of a PyInstaller 6.21.0 Windows/Python-3.12 candidate hash lock without product implementation, then require explicit acceptance of that exact lock/digest before installing it into a cleared isolated build environment; do not add it or its build dependencies to runtime metadata.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Run a complete local cowork session (Priority: P1)

A desktop user can start or continue a local conversation, observe progress as it happens, answer approval and clarification requests, cancel work, and receive a final outcome without starting a network service or exposing local control channels to the conversation view.

**Why this priority**: A trustworthy interactive session is the minimum viable Desktop experience and the foundation for every later workflow.

**Independent Test**: Launch the Desktop app in a clean local profile, create one session, submit a prompt that produces progress plus an approval or question, answer it, and verify that the run completes or can be cancelled while no local network listener is opened.

**Acceptance Scenarios**:

1. **Given** a compatible local runtime and an empty Desktop profile, **When** the user opens the app and submits a prompt, **Then** the app creates a local session, displays normalized progress in order, and reports the terminal outcome.
2. **Given** a run waiting for approval or an answer, **When** the user responds from the Desktop dialog, **Then** the response is applied to that exact pending request and the run continues without a second submission.
3. **Given** an active run, **When** the user cancels it or closes the Desktop app, **Then** pending review waits are released, the run stops, and no orphan local worker remains.
4. **Given** an incompatible or unavailable local runtime, **When** the app starts, **Then** interaction is blocked with a public-safe recovery message and existing local data remains unchanged.

---

### User Story 2 - Organize sessions, projects, and workspaces (Priority: P1)

A desktop user can list, open, resume, inspect, star, fork, and organize persisted sessions in profile-local projects around explicitly selected workspaces. Projects are safe grouping metadata, not filesystem or runtime owners. The app remembers safe references and labels without exposing absolute filesystem paths to the conversation view.

**Why this priority**: Cowork work must survive application restarts and remain associated with the correct user-authorized workspace.

**Independent Test**: Select a workspace, create and complete a session, restart the app, resume the session, submit another turn, fork from a prior point, and verify that all visible workspace data remains label/reference based.

**Acceptance Scenarios**:

1. **Given** a user-selected local folder, **When** the user creates or binds a workspace, **Then** the app stores a private mapping and shows only an opaque identifier, label, availability, and allowed actions in the renderer.
2. **Given** a persisted session associated with an available workspace, **When** the user restarts the app and resumes the session, **Then** subsequent work uses the revalidated workspace and retains prior history.
3. **Given** a persisted session whose workspace is no longer available, **When** the user opens it, **Then** history remains readable, new workspace-dependent work is blocked or requires relinking, and no stale path is silently used.
4. **Given** an existing session point, **When** the user confirms a fork, **Then** a new independent session is created from that point and the source session remains unchanged.
5. **Given** profile-local projects, **When** the user creates, renames, removes, or changes a session's project grouping, **Then** only safe profile grouping metadata changes; sessions, workspace contents, and private workspace bindings remain unchanged.

---

### User Story 3 - Work across panes without unsafe parallel runs (Priority: P2)

A desktop user can keep multiple sessions open in panes, compare history and audit information, use a right-hand inspection area, and navigate with keyboard and focus controls. Only one pane may own an interactive run at a time; other panes remain readable and inspectable.

**Why this priority**: Multi-pane context makes Desktop useful for longer work while preserving the runtime's single-active-run safety invariant.

**Independent Test**: Open three persisted sessions, start a run in one pane, inspect the other two, attempt a second run, switch focus by keyboard, and verify that the second interactive operation is rejected without losing any pane state.

**Acceptance Scenarios**:

1. **Given** multiple persisted sessions, **When** the user opens them in separate panes, **Then** each pane can display history and inspection details independently.
2. **Given** one pane with an active interactive run, **When** the user submits from another pane, **Then** the second run is not started and the app explains which pane currently owns interaction.
3. **Given** an open session, **When** the user opens the right sidebar, **Then** safe context, controls, cost posture, audit, and other available inspection data are shown without altering the conversation.
4. **Given** keyboard-only navigation, high zoom, reduced motion, or forced colors, **When** the user moves among panes, sidebar, dialogs, and composer, **Then** focus remains visible, deterministic, and recoverable.

---

### User Story 4 - Manage capabilities and agent controls safely (Priority: P2)

A desktop user can use the same supported capability settings and agent-control concepts as the Web surface while all accepted permission, plan, budget, workspace, upload, and artifact posture remains authoritative from the host rather than from renderer state.

**Why this priority**: Desktop parity must not create a second enforcement model or misrepresent a draft selection as accepted runtime state.

**Independent Test**: Open capability settings and agent controls, choose an allowed one-run mode, submit a turn, and verify that active and settled posture reflects the host response; repeat with unavailable capabilities and verify honest fallback states.

**Acceptance Scenarios**:

1. **Given** a supported capability or control, **When** the user opens Desktop settings or inspection, **Then** the app shows the same safe status, actions, and unavailable states as the authoritative host projection.
2. **Given** a user-selected one-run control, **When** the user submits a turn, **Then** the choice remains a draft until the host accepts it and applies it only to that accepted run.
3. **Given** a control or capability that is unavailable, **When** the user views it, **Then** the app shows an honest unavailable/read-only state rather than fabricating a value or enabling an unsupported action.
4. **Given** private rules, credentials, paths, rejected values, or configuration, **When** any Desktop status or error is rendered, **Then** those private values are not disclosed.

---

### User Story 5 - Audit, back up, and recover local work (Priority: P2)

A desktop user can inspect a metadata-safe turn audit, create a portable backup of allowlisted Desktop data, validate it, and restore it without risking the current profile. Restored workspace references remain unavailable until the user explicitly relinks local folders.

**Why this priority**: A local-first product must make its durable work inspectable and recoverable without turning backups into a credential or filesystem-path export.

**Independent Test**: Complete several turns, inspect their audit records, create a backup, restore it into a temporary profile, and verify sessions and audit data; then test corrupted, incompatible, path-traversal, symlink, interrupted, and active-run restore cases.

**Acceptance Scenarios**:

1. **Given** a completed or interrupted turn, **When** the user opens its audit view, **Then** the app shows ordered, metadata-safe status and outcome information derived from existing normalized records.
2. **Given** an idle Desktop profile, **When** the user creates a backup, **Then** the app discloses that the portable backup is not application-encrypted and preserves authorized user-, model-, and tool-produced history plus eligible referenced artifacts losslessly, requires an explicit destination, includes only declared allowlisted data plus a versioned integrity manifest, and excludes LoopPlane-owned credentials/configuration, direct/recursive arbitrary workspace collection, private workspace path mappings, unsent drafts, raw internal errors, caches, logs, and process state.
3. **Given** a valid compatible backup, **When** the user restores it, **Then** validation occurs before replacement, the original profile remains recoverable until success, sessions and audit data become available, and workspace references require explicit relinking.
4. **Given** an active run, corrupted archive, unsupported format, unsafe archive entry, or interrupted restore, **When** restore is attempted, **Then** the operation fails safely and the original profile remains unchanged.

---

### User Story 6 - Install and diagnose the Desktop app independently (Priority: P3)

A user can install or launch a built Desktop artifact without relying on a development checkout, external source tree, or separately installed runtime. Missing or incompatible bundled components fail visibly and safely.

**Why this priority**: Feature parity is incomplete if it only works inside the developer environment.

**Independent Test**: Build from a clean dependency state, install or unpack the resulting artifact in isolation, launch it, complete initialization and one credential-free smoke session, then repeat with the local runtime component missing or incompatible.

**Acceptance Scenarios**:

1. **Given** a clean supported system, **When** the user launches the built artifact, **Then** it initializes the local runtime and opens a usable Desktop window without resolving files from the development checkout.
2. **Given** a missing, corrupt, or incompatible bundled component, **When** the app starts, **Then** it displays a public-safe diagnosis, does not hang, and preserves existing profile data.
3. **Given** an unsigned development artifact, **When** validation is reported, **Then** the report distinguishes build and smoke evidence from installer signing, notarization, release, or platforms that were not actually tested.

### Edge Cases

- The local process sends malformed, oversized, duplicated, unknown, or out-of-order messages.
- A response arrives for an unknown, completed, or different session request.
- The local process exits while a run, approval, question, backup, or restore operation is pending.
- The user rapidly opens, closes, reorders, or switches panes while events are arriving.
- The same session is requested in multiple panes or a second pane attempts interaction during the active lease.
- A workspace is moved, deleted, replaced by a link, becomes inaccessible, changes canonical identity, or is no longer authorized.
- A resumed session was created under an older profile or protocol version.
- Cost, budget, agent-control, context, upload, artifact, or capability projections are absent, stale, or unavailable.
- Backup creation runs out of space or is interrupted before finalization.
- Restore input contains path traversal, absolute paths, links, duplicate entries, excessive expansion, invalid integrity data, unsupported versions, or partial data.
- The app is closed during local process startup or protocol negotiation.
- Keyboard focus would otherwise return to an unmounted pane, dialog trigger, or sidebar control.

## Requirements *(mandatory)*

### Functional Requirements

#### Local Runtime and Trust Boundary

- **FR-001**: The Desktop experience MUST run locally without opening a network listener for its renderer-to-runtime communication.
- **FR-002**: A single trusted Desktop owner MUST control local runtime startup, shutdown, input, output, and crash handling. Before reading recovery authority or constructing a Host, the sidecar MUST acquire one generation-external OS-backed exclusive ownership lock for the canonical profile root; a second process for the same profile MUST construct zero Host and fail closed as `busy`, and process crash MUST release kernel ownership without trusting stale lock-file contents. The renderer MUST NOT directly own the local process channel.
- **FR-003**: The renderer MUST be limited to a typed, operation-specific allowlist and MUST NOT have a generic raw-message, process, operating-system, or filesystem escape hatch. Every production/validation window MUST use a restrictive bundled-asset Content Security Policy with no remote script/connect/object/base/form/frame capability, deny unexpected top-frame navigation and every V1 `window.open` request, deny browser permission requests/checks by default, and preserve only the exact packaged local renderer/preload load path.
- **FR-004**: Desktop-to-runtime communication MUST use a versioned request/response protocol with explicit initialization, opaque request correlation, capability negotiation, and ordered notifications.
- **FR-005**: An incompatible protocol major version, unsupported operation, malformed request, or invalid state transition MUST fail closed before interaction and MUST return a bounded public-safe explanation.
- **FR-006**: Runtime progress MUST use the existing normalized event meanings and ordering; this feature MUST NOT add, reinterpret, or re-emit the runtime event bus.
- **FR-007**: Responses and notifications MUST be associated with the correct request and session; stale, duplicate, or unknown identifiers MUST NOT affect another operation, and repeating a mutation request identifier MUST NOT repeat its side effect.
- **FR-008**: Closing the app or losing the local process MUST release pending approvals, questions, subscriptions, active-run ownership, and child-process resources.

#### Sessions and Cowork Interaction

- **FR-009**: Users MUST be able to list, create, open, resume, inspect, rename, star/unstar, search, fork, and delete locally persisted sessions through supported Host actions. Users MUST also be able to create, list, rename, remove, and assign sessions to profile-local Desktop Projects; a project MAY reference one opaque Workspace Reference, one session belongs to at most one project in V1, and removing a project MUST NOT delete its sessions, workspace contents, or private Workspace Binding.
- **FR-010**: Users MUST be able to submit a turn, observe ordered progress, answer approval and question requests, cancel the active turn, and see a terminal outcome.
- **FR-011**: The Desktop profile MUST permit no more than one owning sidecar process and no more than one active interactive run at a time across all panes, renderer views, windows, and attempted second Desktop processes that resolve to the same canonical profile root.
- **FR-012**: The app MUST permit multiple persisted sessions to remain open for history and inspection while enforcing one active interactive pane.
- **FR-013**: A second interactive submission MUST be rejected before a second model run begins and MUST preserve all pane drafts and histories.
- **FR-014**: Forking MUST require an explicit source point and confirmation, create an independent target session, and leave the source unchanged.
- **FR-015**: The right sidebar MUST expose only available public-safe inspection data and MUST not mutate conversation or runtime state merely by opening.
- **FR-016**: Keyboard and focus behavior MUST support pane switching, composer access, dialogs, inspection, and settings without trapping focus or losing a recoverable focus target.
- **FR-017**: The Desktop experience MUST preserve the existing bilingual, high-zoom, reduced-motion, forced-color, and assistive-technology behavior of reused presentation surfaces.

#### Capabilities and Agent Controls

- **FR-018**: Desktop capability settings and agent controls MUST consume host-owned projections and actions rather than creating renderer-owned policy state.
- **FR-019**: A client-selected one-run option MUST remain a draft until host acceptance and MUST apply only to the accepted run.
- **FR-020**: Permission, plan, budget, workspace, upload, artifact, and capability enforcement MUST remain outside the renderer.
- **FR-021**: Unavailable, unknown, unpriced, or unreadable values MUST be represented honestly and MUST NOT be displayed as zero, allowed, active, or configured.
- **FR-022**: LoopPlane-owned private rules, credentials, configuration content, absolute paths, rejected sensitive input, and raw internal errors MUST NOT appear in renderer-visible status, audit, logs, protocol errors, manifest metadata, or documentation. Authorized conversation and referenced-artifact surfaces MAY losslessly display user-, model-, or tool-produced content that itself contains sensitive values or workspace excerpts; those payloads MUST NOT leak into any secondary status, audit, diagnostic, error, log, or metadata surface and MUST be covered by the unencrypted-backup disclosure.

#### Projects, Workspaces, and Resume

- **FR-023**: Users MUST select local workspace folders through a trusted Desktop-owned interaction rather than by typing an unrestricted path into the renderer.
- **FR-024**: A selected workspace MUST be canonicalized, validated, and represented to the renderer by an opaque identifier, safe label, availability, and allowed actions.
- **FR-025**: The private opaque-identifier-to-path mapping MUST be owned outside the renderer and scoped to the local Desktop profile.
- **FR-026**: Resuming interactive work in a workspace MUST use a currently validated scope; a missing, moved, or unauthorized workspace MUST NOT silently fall back to a stale path. Any persisted revalidation result, including availability or private binding validation timestamps/state, MUST pass through the Profile Mutation Lease writer gate.
- **FR-027**: Existing host resume behavior MUST remain unchanged when the Desktop-specific validated scope is not supplied.
- **FR-028**: Raw workspace paths MUST NOT be added to runtime events, checkpoints, existing Web projections, or browser-visible contracts.
- **FR-029**: The trusted Desktop/runtime boundary MUST generate one opaque principal identity per local profile, retain it across restarts and backup/restore, and prevent the renderer from selecting, replacing, or impersonating another principal.
- **FR-030**: Workspace relinking MUST be explicit, preserve the opaque reference where safe, and leave session history readable when relinking is declined or fails.

#### Turn Audit and Recovery

- **FR-031**: The turn audit MUST be a metadata-safe read model derived from existing normalized records and outcomes; it MUST NOT create a second runtime event source or alter recorded history.
- **FR-032**: Audit entries MUST preserve stable ordering and identify the related session, turn, status, and outcome without exposing private payloads.
- **FR-033**: Backup creation MUST be an explicit user action and MUST include a declared allowlist plus a versioned manifest and integrity information. From lease acquisition through archive finalization, backup MUST exclude every active-generation writer—session rename/star/fork/delete/create, interactive submit/answer, Project/workspace mutation (including persisted workspace revalidation), capability action, and competing backup/restore—so the Host snapshot and Desktop profile metadata represent one consistent state; only bounded shutdown/cancel/release teardown may bypass the writer gate.
- **FR-034**: Portable backups MUST exclude LoopPlane-owned credentials, provider tokens, private configuration, recursive/arbitrary workspace contents, private workspace path mappings, raw internal errors, renderer caches, unsent pane drafts, logs, process identifiers, and transient active-run state. Full session history and eligible referenced LoopPlane artifacts MUST remain lossless; because user-, model-, or tool-produced content may itself contain credentials, paths, workspace excerpts, or other sensitive values and 078 does not add application-level backup encryption, creation MUST disclose both limitations and require an explicit user-approved destination.
- **FR-035**: Restore MUST validate compatibility, integrity, archive-entry safety, and declared limits in a staging area before replacing current data.
- **FR-036**: Restore MUST reject unsafe links, path traversal, absolute paths, duplicate/conflicting entries, unsupported versions, invalid integrity data, and archives that exceed declared safety limits.
- **FR-037**: Restore MUST be blocked while an interactive run or another profile mutation is active. Once `restore.validate` reserves ownership, every RPC capable of writing the active generation or generation-external profile state MUST fail `busy` before dispatch until the owning commit/cancel/expiry/shutdown path releases the reservation; safe teardown is the only exception.
- **FR-038**: A failed or interrupted restore MUST preserve or deterministically recover the previous profile from exact journal authority, including exact previous active-pointer/proof bytes and a usable Host rooted at that generation; without such authority it MUST fail locked with zero Host rather than select a retained directory. Before initial or restore pointer publication, the platform-scoped publication protocol MUST complete: POSIX local filesystems MUST flush regular files/directories and both rename parents for the declared physical-power-loss guarantee, while Windows MUST use documented regular-file flush, supported-local-volume write-through move/replace, and reopen/current consistency checks for a process/application-crash guarantee and MUST explicitly disclaim sudden physical-power-loss persistence of both parent-directory entries. Publication MUST produce a canonical immutable receipt bound into pointer/proof/journals, but the active generation remains mutable and restart MUST validate current schema/SQLite/artifact consistency rather than publication-time hashes. A fresh zero-session bootstrap MAY declare checkpoint SQLite and artifact state `absent_uninitialized`; before the first Host, the sidecar MUST call a public non-instance `loopplane.host` active-generation validation facade that proves the declared pristine absence rather than create/open private stores. The same facade MUST validate initialized current generations through dedicated read-only schema/SQLite ownership/artifact-consistency checks without constructing a Host or normal store, creating/mutating files, or returning storage handles/paths; only normal Host/store ownership may create stores on first durable use. Fresh bootstrap MUST reread its matching proof and pointer before the first Host. Before restore-candidate publication, two independently checksummed full-preimage recovery records MUST be valid; state changes MUST be copy-on-write, and a candidate MUST remain inactive unless a proof matching its exact pointer and publication receipt is written after candidate Host readiness/install. If proof write/flush may have succeeded but acknowledgement is uncertain, the process MUST perform no rollback/cleanup/binding mutation and startup MUST adjudicate proof-versus-journal recovery.
- **FR-039**: A successful restore MUST make allowlisted sessions, preferences, and audit data available while leaving every workspace reference `relink_required` until explicit relink. That state MUST be checked before any device-private binding lookup, so an old binding with identical profile/workspace IDs cannot be revived; stale-binding cleanup MUST wait until candidate proof authority so rollback remains possible.

### Key Entities

- **Desktop Profile**: The local user's durable Desktop state, including safe preferences, profile-local projects, opaque workspace references, and Desktop-owned metadata; it has one fixed local principal and excludes unsent drafts, secrets, and transient process state.
- **Profile Ownership Lock**: A generation-external OS-backed exclusive process lock for one canonical profile root, acquired before recovery/store/Host work; contention produces public-safe `busy` with zero Host, and kernel crash release permits only a later full recovery.
- **Profile Mutation Lease**: The owning sidecar's transient all-writer gate for session, interaction, Project, workspace, capability, profile, backup, and restore mutations; backup and restore hold it for their complete normative windows.
- **Desktop Project**: A safe profile-owned grouping with opaque identity, label, optional Workspace Reference, and session membership. It never owns a filesystem path, runtime policy, session records, or workspace contents; deleting it leaves grouped sessions and workspace data intact.
- **Local Session**: A persisted conversation with identity, title, history, model/context metadata, lifecycle state, optional fork source, and one active-interaction lease at most.
- **Workspace Reference**: An opaque Desktop-profile identifier plus safe label, availability, and actions; its canonical local path mapping is private and must be revalidated before use.
- **Pane**: A view onto one persisted session with draft, focus, inspection, and read-only/interactive state; multiple panes may exist but only one may own active interaction.
- **Turn Audit Record**: Ordered, metadata-safe information about a session turn and its outcome, derived from existing records without copying private payloads.
- **Backup Manifest**: A versioned declaration of allowlisted backup entries, compatibility, integrity information, limits, and creation metadata; it contains no LoopPlane-owned credentials or private workspace path mappings and records that user-, model-, or tool-produced authorized content and eligible referenced artifacts are preserved losslessly while unsent drafts are excluded.
- **Restore Transaction**: A staged validation and replacement attempt that reserves the profile-mutation lease until commit, cancel, expiry, or cleanup; it retains two copy-on-write full previous pointer/proof preimages until an independent proof authorizes the candidate, allowing exact rollback or fail-locked startup without generation guessing.
- **Desktop Runtime Owner**: The trusted sidecar holder of the sole live Host and generation-specific Host factory. Restore success swaps it to a freshly verified candidate-rooted Host; rollback retains or reconstructs a previous-generation Host before requests resume.

## Success Criteria *(mandatory)*

## Assumptions

- The primary user is a single local operator using one Desktop profile and one application window with multiple panes; multi-window, multi-user, and remote identity are deferred to later units.
- The existing host, checkpoint, capability, cost, approval/question, and agent-control semantics remain authoritative and reusable.
- Multiple panes are a presentation and inspection feature, not permission for multiple concurrent interactive host runs.
- Portable backups prioritize recoverability and honest privacy boundaries: they preserve full session history, eligible referenced LoopPlane artifacts, profile-local projects, the profile-owned opaque principal, opaque workspace references, and safe labels/preferences; they exclude unsent drafts, LoopPlane-owned credentials/configuration and private path mappings, require folder relinking after restore, and warn that unencrypted user-, model-, or tool-produced content may retain credentials, paths, workspace excerpts, or other sensitive values.
- Desktop backup never directly or recursively collects workspace contents. Eligible checkpoint-referenced Gateway artifacts may already contain tool-produced workspace excerpts and remain lossless under the explicit unencrypted-sensitive-content disclosure; users manage repository or filesystem backups separately.
- Existing Web presentation behavior may be reused only through a narrow boundary that preserves Web behavior and does not make Desktop depend on a live Web server.
- Unsigned Windows GUI/package smoke evidence is sufficient for 078; signing, notarization, publishing, other-platform claims, and release remain maintainer-controlled follow-ups. PyInstaller is treated as an existing packaging mechanism whose exact direct version and complete Windows/Python-3.12 transitive hashes are approved only for a cleared isolated build environment, not as runtime metadata.
- POSIX generation publication may claim exercised physical-power-loss durability through file/directory `fsync`; Windows 078 claims documented process/application-crash consistency on supported local filesystems and fail-closed startup verification, not sudden physical-power-loss persistence of both parent-directory metadata entries.
- A separate ADR/human gate is mandatory because this unit introduces a private process protocol, Desktop profile boundary, workspace path ownership, interactive resume seam, and backup/restore semantics.
